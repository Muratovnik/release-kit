# Политика аудита, области и приватные overlay

Канонической остаётся [английская версия](../audit.md). Для первой проверки используйте
[минимальную настройку CLI](../../README.ru.md#первая-проверка-в-существующем-проекте).
Команда `audit` объединяет правила проекта с поиском секретов Betterleaks и офлайновой
проверкой локальных ссылок Lychee. `exposure` и `overlay` — более узкие диагностические
команды, а не замена объединённому публикационному гейту.

Встроенные текстовые правила ищут конкретные шаблоны, нормализуют отдельные фрагменты
текста и применяют объявленные владельцем точные значения и регулярные выражения. Они не
выполняют понимание языка в общем виде и не выгружают дерево или приватную политику в
LLM. Успешный результат подтверждает только настроенные проверки на исследованной области.

## Конфигурация

`relkit.toml` принадлежит защищаемому репозиторию. Ниже **расширенный пример**, а не
обязательный набор по умолчанию: объявляйте только те правила, которые осмысленны для
вашего проекта.

```toml
[exposure]
private_paths = [".private", ".codex"]
private_files = ["AGENTS.local.md", ".mcp.json"]
private_suffixes = [".local.md"]
required_ignores = [".private", ".codex", "AGENTS.local.md", ".mcp.json"]
allowed_users = ["example-owner"]
owner_identities = ["Example Maintainer <maintainer@example.invalid>"]
forbid_png_metadata = true
forbid_ai_attribution = true
forbid_internal_planning = true
forbid_machine_observations = true
provenance_required = ["tests/generated/*", "docs/screenshots/*"]
betterleaks_config = ".betterleaks.toml"

# Deliberate synthetic fixtures where structural rules are not meaningful.
# This does not suppress the secret scanner or non-excludable owner findings.
exclude = ["tests/fixtures/*"]

# Adoption debt can only shrink; a stale entry also fails.
[exposure.baseline]
"legacy/config.toml" = ["home-directory"]

# A public provider name is allowed only on declared product surfaces.
[exposure.providers.Someservice]
role = "product-data-provider"
allowed_surfaces = ["src/*", "docs/*", "tests/provider/*"]

# These declarations record review; they do not anonymize or generate files.
[exposure.provenance]
"tests/generated/*" = "synthetic"
"docs/screenshots/*" = "anonymized"
```

Имя провайдера не становится приватным только потому, что владелец пользуется его
сервисом. Словарь ролей провайдера закрыт: рабочий процесс, принадлежащий владельцу,
нельзя переобъявить как продуктового провайдера. Материал, объявленный как
`machine-derived`, остаётся находкой и должен быть заменён до публикации; `anonymized` —
это утверждение проекта о том, что проверка состоялась, а не автоматическая гарантия
анонимизации.

### Идентичности коммитов и атрибуция

`forbid_ai_attribution` проверяет дерево, историю файлов, аннотированные теги и коммиты.
Атрибуция в коммите — заявление того, кто его сделал, поэтому `owner_identities`
объявляет владельцев в написании `Name <email>`, которое печатает Git, и тогда:

- в сообщении и заголовках коммита, автор которого — владелец, нет атрибуции ИИ;
- коммит, который владелец создал как автор или committer, не называет инструмент ИИ
  ни автором, ни committer;
- коммиты всех остальных, включая тестовый merge, который хостинг собирает для их
  pull request, на атрибуцию не проверяются. Добавленные ими файлы — проверяются.

Хотя бы одна объявленная идентичность должна быть автором коммита в области истории.
Иначе опечатка в записи освободила бы от проверки все коммиты, поэтому аудит вместо
этого проваливается. Без `owner_identities` правило для сообщений проверяет все коммиты.

`allowed_identities` — другой, закрытый список: в нём должны быть все авторы, committer
и авторы аннотированных тегов в области истории. Он подходит истории, которую больше
никто не пишет. С ним проваливается любой pull request стороннего участника и любая
проверка pull request, которая идёт на тестовом merge, закоммиченном хостингом под
собственной идентичностью.

Значения по умолчанию включают проверки секретов и ссылок. Обычный `.betterleaks.toml`
расширяет поддерживаемые значения по умолчанию:

```toml
title = "project secret scanning"
betterleaksMinVersion = "1.8.1"

[extend]
useDefault = true
```

Держите списки разрешений для секретов узкими, нацеленными на правило, путь или
значение. Структурные шаблоны `exclude` — не списки разрешений для сканера секретов.
Базовые линии фиксируют существующий долг внедрения; исключения описывают места, где
структурное правило неуместно. `--strict` также проваливает прогон при оставшихся
базовых линиях. Недействительные или устаревшие записи базовой линии не создают
постоянного зелёного исключения.

## Области

```text
python .github/relkit.pyz audit
python .github/relkit.pyz audit --staged
python .github/relkit.pyz audit --history
```

Область рабочего дерева включает отслеживаемые файлы и неотслеживаемые, но не
игнорируемые кандидаты на публикацию. Область индекса читает индекс Git: `relkit.toml`,
конфигурация Betterleaks и её относительные файлы политики должны быть проиндексированы.
Неиндексированные правки политики в этот вердикт не входят. Betterleaks сканирует
проиндексированные изменения; политика и Markdown исследуют индекс.

Области истории нужны чистое дерево **отслеживаемых** файлов и полная локальная история.
Она проверяет текущий `HEAD`, локальные и удалённые ветки, теги, заметки Git, а также
забранные ссылки pull-запросов GitHub, merge-запросов GitLab и изменений Gerrit. Имена
ссылок, сообщения аннотированных тегов и личности создателей тегов проверяются наравне с
коммитами и блобами. Синтетические контрольные точки клиентов намеренно лежат вне этой
области. Неотслеживаемые, но не игнорируемые файлы всё ещё может исследовать проход по
кандидатам рабочего дерева; частью истории Git они от этого не становятся. История
отвергает усечённые клоны, ссылки замены и непустые трансплантаты Git, а также отключает
семантику замены в своих процессах Git и сканеров.

Перед проверкой восстановления заберите ссылки, существующие только на хосте: локальные
проверки не могут исследовать объекты, которых у клона нет. Ни сканирование истории Git,
ни его проверка ссылок не покрывают issues на хостинге, журналы Actions и независимо
загруженные релизные файлы. Об этих отдельных поверхностях см.
[publication review](../publication-review.md) (English).

CI обычно использует `--history` без `--owner`: публичный клон не может знать приватных
значений владельца. На проверенной установке владельца используйте:

```text
python .github/relkit.pyz audit --history --owner
python .github/relkit.pyz audit --history --owner --require-overlay
```

Режим владельца дополнительно требует приватной политики и корректно установленной
защиты. `--require-overlay` требует ещё и точного манифеста примонтированных ссылок. Для
[базового аудита по публичной политике](../../README.ru.md#первая-проверка-в-существующем-проекте)
эти флаги не нужны.

### Архивы и внешние объекты

Контейнеры семейства ZIP распознаются по содержимому в рабочем дереве, индексе и
достижимой истории: `.zip`, `.whl`, `.jar`, `.pyz`, пакеты Office и OpenDocument, а также
ZIP без расширения. Небезопасные пути и символические ссылки внутри записей, повреждённые
или превышающие бюджет контейнеры, приватные пути и срабатывания текстовых правил
проваливают проверку, включая вложенные в пределах лимита ZIP и записи в Unicode.
Диагностика называет и внешний артефакт, и запись.

`forbid_png_metadata`, если он включён, проверяет также записи PNG и достижимые
исторические PNG и архивы. Его структурные исключения продолжают действовать.

Неподдерживаемые сжатые форматы (в том числе tar/gzip, 7z и RAR) проваливают проверку,
вместо того чтобы получить вердикт по недекодированным байтам. Повреждённые или
превышающие бюджет объявленные ZIP — это неисключаемый сбой проверки.

Указатели Git LFS и gitlink-и подмодулей проваливают проверку, потому что их внешнее
содержимое не хранится в исследуемых блобах Git. Проверяйте внешние репозитории как
отдельные корни; материал LFS исследуйте или переносите явно. Такие сбои и находки по
приватной политике владельца нельзя принять через базовую линию или структурное
исключение.

`--no-download` превращает отсутствие проверенных кэшей движков в операционный сбой. О
закреплении платформ, целостности кэша и явном переопределении исполняемых файлов см.
[distribution details](../distribution.md#scanner-platform-and-cache-behavior) (English).

## Приватная политика владельца

Приватной топологии, точным запрещённым значениям, рабочим процессам владельца и
выражениям для персональных данных не место в публичной конфигурации. В режиме владельца
корень политики определяется в таком порядке:

1. Непустая переменная `RELKIT_PRIVATE_ROOT`. Относительное значение сохраняет исходное
   поведение совместимости и разрешается от родительского каталога публичного клона.
2. Единственное значение `releasekit.privateRoot` из локальной конфигурации Git
   публичного репозитория. Относительное значение разрешается от корня публичного клона.
3. Соглашение о соседнем каталоге `../<имя-клона>-private`.

Команды CLI для владельца и overlay, установленная защита владельца, аудиты владельца в
координаторе и запросы владельца через MCP используют этот же порядок выбора.

Задать постоянный выбор для репозитория, не создавая отслеживаемого файла в проекте:

```text
git config --local releasekit.privateRoot "<absolute-owner-policy-path>"
```

Глобальная и системная конфигурация Git, а также включаемые файлы источниками политики не
являются. Отсутствие локального ключа разрешает запасной вариант с соседним каталогом.
Дублирующиеся, пустые, некорректные или нечитаемые локальные значения отказывают в
проверке владельца — как и настроенный каталог, которого нет; некорректный настроенный
выбор никогда не подменяется соседним каталогом. Для корня вне Git поиск в локальной
конфигурации пропускается, а варианты с переменной окружения и соседним каталогом
работают и без Git.
Связанные рабочие деревья разделяют локальную конфигурацию репозитория, поэтому
используйте абсолютный путь, когда все рабочие деревья должны выбирать одну политику.
Относительное локальное значение намеренно разрешается от собственного публичного корня
каждого рабочего дерева.

Выбранный корень владеет файлом `.publication-private-values` и, при необходимости,
манифестом ссылок `install.conf.yaml`. Точные значения могут включать имена рабочих
пространств, приватные пространства имён, идентификаторы записей и фрагменты путей; сам
список публиковать нельзя.

Тот же корень может содержать `.publication-owner.toml`:

```toml
version = 1
owner_workflows = ["OwnerWorkbench"]

[[patterns]]
name = "private-record-reference"
kind = "personal-data"
expression = '''\brec_[0-9a-f]{12}\b'''

[[patterns]]
name = "local-inventory-observation"
kind = "machine-observation"
expression = '''(?i)observed on the maintainer's machine'''
```

Виды шаблонов: `owner-workflow`, `personal-data` и `machine-observation`. Режиму владельца
нужно хотя бы одно точное значение, рабочий процесс или шаблон; пустая или отсутствующая
политика не может дать чисто структурного прохождения в режиме владельца. Оба имени
файлов политики владельца безусловно приватны, если найдены в публичном дереве или архиве.

Человеческое авторство, метаданные лицензии и собственная публичная идентичность проекта
нарушением анонимности не являются. Что не может покинуть периметр — решает владелец.
Сканер не может принять это решение, опираясь только на встретившееся в тексте имя.

## Защита репозитория

Устанавливайте защиту только после проверки её входных данных и получения отдельного
разрешения на изменение хука, если оно требуется:

```text
python .github/relkit.pyz protect install --dry-run
python .github/relkit.pyz protect install --plan-hash REVIEWED
python .github/relkit.pyz protect check
```

Установленная защита живёт в `<git-common-dir>/hooks/pre-push` и запускает гейт по истории
с обязательной приватной политикой владельца. Для базовой установки CLI она не нужна. Она
закрепляет отслеживаемую проекцию, `relkit.toml`, настроенную политику секретов и — для
релизной конфигурации на основе workflow — публикующий workflow. Проверенные изменения
закреплённых входных данных требуют явного
[обновления защиты](updates.md#уже-изменённые-файлы-и-дрейф-защиты).

Если `core.hooksPath` перенаправляет Git в другое место, внешний владелец обязан сначала
предоставить исполняемый диспетчер с
`# git-common-dir-hook-dispatcher: pre-push v1`. Release-kit проверяет совместимость,
прежде чем записать свою защиту репозитория; он никогда не создаёт и не заменяет внешний
диспетчер. Защита разрешает `python`, `python3` или `py`. Более старые поддерживаемые
шаблоны защиты продолжают применять свои закрепления, пока их явно не обновят. О модели
владения до 0.5.0 см. [процедуру миграции](updates.md#миграция-владельца-хука).

Локальная защита pre-push не является серверной защитой веток. Не обходите её и не
ослабляйте политику владельца, чтобы провести релиз.

## Контракт overlay

Файл Dotbot `install.conf.yaml` в приватном соседнем каталоге — единственный список
монтирований. Release-kit проверяет, что каждое монтирование `target: source` существует
как символическая ссылка или junction Windows, разрешается в **точный** источник из
манифеста, игнорируется и не отслеживается публично и указывает на путь, отслеживаемый
приватным репозиторием. Просто разрешиться куда-то внутрь приватного корня недостаточно.

Ссылки создаёт Dotbot; release-kit их проверяет. Проекты с overlay на копировании или
синхронизации могут принять публикационные проверки независимо; изменение модели владения
и монтирования — отдельная миграция. `relkit overlay` диагностирует этот контракт, ничего
не чиня.

### Форматы манифеста и совместимость с YAML

Прежний построчный читатель YAML мог пропустить более поздний блок, содержащий
комментарий, ключ в кавычках или flow-отображение. Он больше не используется. Документ
разбирается целиком до того, как будет возвращено хоть одно монтирование; неподдерживаемая
ссылка в любом месте отвергает весь список.

JSON обрабатывается стандартной библиотекой Python. Dotbot принимает JSON наравне с YAML,
поэтому тот же проверенный `install.conf.yaml` может содержать JSON — без второго списка и
без изменения того, как release-kit находит приватный корень. Например:

```json
[{"link": {"../public/.someclient": "local/.someclient"}}]
```

Для существующего YAML установите дополнение `overlay-yaml` из проверенного клона
исходного кода в то изолированное окружение Python, которое фактически исполняет CLI:

```text
python -m pip install "<reviewed-source-checkout>[overlay-yaml]"
```

Дополнение закрепляет PyYAML 6.0.3. Его безопасный загрузчик разбирает синтаксис YAML;
release-kit лишь проверяет явные безусловные пары «назначение — источник». Дублирующиеся
ключи отображения, неявные и расширенные цели, условные и glob-умолчания для ссылок, а
также подстановки окружения и домашнего каталога получают отказ вместо частичного
вердикта. Загрузчик никогда не исполняет команды Dotbot и теги объектов Python в YAML.
Отсутствие PyYAML — это ошибка, требующая действия, а не разрешение игнорировать блок.
Базовым командам CLI и overlay в JSON дополнение не нужно.

**Совместимость:** обновление одного лишь zipapp не устанавливает PyYAML. Проверьте
исполняющий интерпретатор, включая интерпретатор хука, прежде чем принимать это изменение.
В существующем зафиксированном окружении SDK собранного плагина PyYAML нет: используйте
для этого пути JSON в общем манифесте либо отдельно установленный автономный адаптер с
`[mcp,overlay-yaml]`. Не правьте lock установленного плагина и не подавляйте ошибку
непроверенной глобальной установкой. Ни один манифест не переписывается и не
переименовывается автоматически. Необязательная миграция YAML в JSON на месте обязана
сохранить весь документ Dotbot, а не только его ссылки, и остаться явным изменением,
проверенным владельцем.

Эта зависимость намеренно необязательна и не заменена встроенной реализацией YAML. См.
[форматы Dotbot](https://github.com/anishathalye/dotbot#configuration) и
[безопасную загрузку PyYAML](https://pyyaml.org/wiki/PyYAMLDocumentation).

## Диагностические интерфейсы и автоматизация

`relkit exposure` выполняет только встроенные проверки политики и остаётся для диагностики
и совместимости. Для объединённых релизных проверок и CI используйте `audit`. Извлечение и
проверка заметок к релизу вынесены отдельно, потому что им нужна запрошенная версия; см.
[notes](../notes.md) (English). Любая команда может перейти на
[структурированный результат CLI](../cli-json.md) (English), чья семантика кодов возврата
и статусов входит в публичный интерфейс. Ошибка конфигурации или выполнения не является
свидетельством безопасности.
